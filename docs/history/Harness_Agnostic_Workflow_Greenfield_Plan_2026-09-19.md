# Harness-agnostic Agentic Development Workflow：从零重写方案

**方案代号：HFlow（暂定，未核查命名冲突）**  
**日期：2026-09-19（America/Los_Angeles）**  
**定位：DSH-first，Harness-neutral，成本与交付优先**  
**文档性质：GitHub 调研后的设计与实施基线，不是已完成的实现或兼容性认证。**

> 核心决策：新建仓库，不修复、不重构、不搬运旧运行器。复用原生 Harness、标准传输、Git、SQLite 和已有测试工具；只新写任务准入、预算、证据和交付语义这层小型控制器。第一版不要求 Codex、不要求多 Agent、不部署全局配置、不自动修复工作流自身。

## 1. 这次到底要解决什么

### 1.1 用户提供的事实

你表示，旧工作流消耗了约 90% 的 Codex 周额度，但实际推进很少，主要支出来自工作流修复、代理重试、重复验证和材料整理。这里没有获得逐请求账单或运行记录，所以不能把这四项换算成已经测量的精确占比，也不能把剩余额度推定为精确可调用次数。

本次目标不是“更完整的工作流平台”，而是：**把更多预算用于可以验收的项目改动，把失败控制在局部，不再为维护工作流持续支付模型费用。**

### 1.2 成功定义

新系统必须回答四个问题：本次交付是什么？花费由哪些可观察活动构成？为什么需要这些活动？失败后是否会继续花钱？

主要成功指标是“达到同等验收标准的一项任务所消耗的模型调用、人工介入和总耗时”。Agent 数量、规则数量、文档数量、生成代码行数、测试执行次数，都不能代替交付指标。

### 1.3 绿地重写边界

新仓库不继承旧目录树、安装脚本、运行状态、历史认证格式、固定模型路由、全局部署结构。旧仓库只提供三个输入：确实发生过的故障案例、用户仍需要的产品约束、能够独立理解的验收场景。

**禁止把“旧实现完整搬进新目录，再逐渐解耦”称为重写。**

### 1.4 第一版与最终愿景

最终愿景保留跨 Harness Agent Team，以及 Worker 内部使用原生 Subagent 的混合架构。第一版只交付一个完整纵切面：一个任务、一个原生 DSH Worker、程序验证、按风险选用独立审查、清晰的本地交付结果。

第二个真实 Harness 接入之前，只能称为“按 Harness-agnostic 设计的 DSH 实现”，不能声称已经证明了跨 Harness 通用性。

### 2.2 三个会改变设计的发现

**发现一：DSH 已经提供原生 ACP。**

本次读取的 DSH 契约支持初始化、建立会话、列出/恢复/关闭会话、提交/取消任务、模型配置和语义事件。它支持 `session/resume`，但明确不支持 `session/load`、历史事件回放、fork 和多工作目录等部分能力。必须按能力协商使用，不能认为“支持 ACP = 所有 ACP 扩展都能用”。[S3]

**发现二：acpx 值得复用，但默认行为不全符合本项目。**

acpx 允许启动任意 ACP 服务，其自定义 Agent 文档覆盖 `session/resume` 或 `session/load`。同时，CLI 文档说明，重连失败时可能自动回退到新会话；Flows 标为 experimental，回放查看器是观察历史，不等于已证明的崩溃后恰好执行一次。首版采用显式一次性执行，关闭自动续跑策略；后续只有能够识别并拒绝意外 session replacement 时，才启用持久续接。[S5–S8]

**发现三：名称像 workflow 的项目不一定是你需要的 workflow。**

DSH 的 `dsh-plugin-agent-workflow` 是观测 UI，不是调度器。`dsh-agent-teams` 是实际的原生团队编排，但其范围检查是完成时审计，不是操作系统写入拦截；它自己的自动恢复和质量门需要纳入总预算。不能因为装上插件，就宣称已经解决预算隔离与写入边界。[S16–S17]

### 2.3 对旧仓库的准确判断

当前 README 已有共享 `core/reuse/` 协议和 Team 运行器，不能再说“完全没做复用”。最新读取的兼容性修改也不再仅凭版本号不同就阻止运行，这一点应该承认。[S1–S2]

然而，当前结构仍保留多套 Harness 落地和全局部署路径；Team 运行器部署到 Codex 家目录，Lead 证据逻辑读取 Codex 的线程/会话元数据。这些可见事实表明，部署、角色身份、运行证明和具体 Harness 仍有耦合。[S1–S2]

本次不会为了修掉这些耦合，再开启一轮旧运行器修复工程。保留问题样本即可。

## 3. Reuse / Adapt / Build：本项目自身的复用决策

| 能力 | 决策 | 原因与边界 |
|---|---|---|
| 模型交互、工具循环、上下文压缩 | Reuse：原生 DSH，之后原生 Codex 等 | 这是 Harness 的职责，不由新项目重写 |
| Agent 客户端传输 | Reuse 优先：acpx + DSH ACP | 官方 DSH 已暴露协议，先验证互操作性 |
| DSH 一次性备用传输 | Adapt：官方 headless | 仅当首选兼容性门未通过时选用，不同时维护两条生产路径 |
| ACP JSON-RPC 实现 | 不自研 | 不从零实现协议栈；必要时另立 ADR 评估官方 SDK |
| Git 隔离与变更交付 | Reuse：Git 原生命令 | 自写的只是授权、调用和结果校验 |
| 状态事务 | Reuse：SQLite | 不自制文件锁数据库，不同时写几份状态事实源 |
| 数据契约校验 | Reuse：Pydantic | 模型声明一次，生成 JSON Schema |
| lint / test / build | Reuse：目标项目现有命令、CI | 不再为每个阶段另造同义检查 |
| 通用 DAG / 分布式队列 | 首版不做 | 单机顺序闭环不需要分布式编排框架 |
| 任务准入、证据缓存、预算与结果接受 | Build：小型领域控制器 | 已调研工具不能直接替代本项目的这组特定约束 |
| 看板、向量记忆、插件市场 | 首版不做 | 没有证据证明其收益超过维护成本 |

“Build 小控制器”不是无限造轮子的豁免。新增模块必须说明：现成组件缺少哪个必要语义、为何不能用配置或薄适配补齐、引入该模块后可删除哪些人工/模型动作。不能一句“扩展性更好”就批准。

首版生产传输只有一种。M0 选择完成后，把选择和版本写入 ADR；未选路径只保留调查记录，不写第二套完整代码。

## 4. 目标架构：薄控制层，原生执行层

```text
人 / 当前 DSH 对话 / CLI
             │  提交一次任务、一次预授权策略
             ▼
       HFlow 确定性控制器
       ├─ 任务与复用准入
       ├─ 预算与权限检查
       ├─ 工作区与执行尝试
       ├─ 验证证据与按需审查
       └─ 接受、交付、状态与报告
             │
       中立 Driver 契约
             │
       Transport 适配层
       ├─ 首选 acpx → 官方 DSH ACP
       ├─ 若 M0 不通过：官方 DSH headless（替代，不叠加）
       └─ 后续：其他原生 Harness 的适配器
             │
       原生 Harness / 原生 Agent
       └─ 可选原生 Subagents（后续能力，受父预算约束）
```

### 4.1 必须拆开的概念

`Role` 是做什么，例如 implementer/reviewer。`Harness` 是在哪套原生执行环境工作。`Model` 是该环境选择的推理模型。`Transport` 是怎样通信。`Workspace` 是在哪里读写。`Policy` 是什么行为被允许。`Task` 是最后必须交付什么。

角色不能命名为“Claude Author”或“Codex Lead”。正确表达是 `role=reviewer`，由本机 profile 绑定 `harness=dsh` 或其他 Harness。模型 ID 来自当前配置/原生目录，不写进核心状态机。

### 4.2 谁负责什么

控制器负责确定性工作：状态、锁、计数、指纹、预算预留、子进程生命周期、测试命令、证据归档、报告格式化。这些不调用 LLM。

Agent 负责需要语义判断的工作：理解需求、选择实现、编写代码、解释真实失败、判断方案和变更中的语义风险。

Harness 负责它已有的能力：工具调用、会话、上下文、原生 Subagent、原生权限机制。控制器不复制这一层。

### 4.3 不是“只剩最低共同能力”

核心定义能力请求而不是假定能力一致。例如：`fresh_session`、`cancel`、`native_subagents`、`model_selection`、`billing_usage`、`readonly_enforcement`。

每项能力记录 `documented / probed / enforced / unsupported / unknown` 中适合的状态，以及平台、版本、profile 指纹。只有协议文档不等于在本机执行过；一次成功调用不等于安全边界受到强制执行。

无法满足必要能力时拒绝这一种运行模式。可以执行另一种已经授权的低能力模式，但不得静默把“强只读审查”换成“提示词要求只读”。

### 4.4 当前 DSH 对话如何使用它

你仍然可以在 DSH 中用自然语言描述目标。当前会话最多整理一次短 TaskSpec，再调用前台运行命令等待结果；它不是每几十秒调用一次模型、阅读 worker 日志、重写进度表的常驻经理。

小任务不额外创建 Planner。用户已经给出的验收条件直接使用。只有需求实质不明确、引入新组件或高风险设计时，才安排一次有预算的规划/研究阶段。

## 5. 技术栈与项目结构

### 5.1 推荐固定选择

建议控制器使用 **Python 3.12+**，运行时用标准库 `sqlite3`、`subprocess`、`argparse`、`hashlib`、`pathlib`，数据契约使用 Pydantic。开发测试使用 pytest；进程枚举等功能只有实际需要时才添加经过验证的跨平台依赖。

选择 Python 是为了用较小的本地程序表达状态与系统调用，不是因为 Python 才能做到通用。DSH/acpx 仍使用它们自己的运行环境。核心不依赖 DSH 的 TypeScript 内部包，因此上游内部重构不直接进入控制器依赖树。SQLite 和 subprocess 的基础能力由 Python 官方库提供；进程树安全终止并不是调用一次 subprocess 就自动解决的问题。[S19–S21]

不要在首版同时维护 Python、TypeScript、PowerShell 三套核心。PowerShell 最多用于用户入口或平台验收脚本，不保存业务状态和调度语义。

### 5.2 新仓库目录

```text
hflow/
  pyproject.toml
  README.md
  AGENTS.md                  # 简短导航，不复制整份方案
  src/hflow/
    cli.py
    contracts.py             # 唯一的数据契约定义
    controller.py            # 有限状态机，不是通用工作流 DSL
    store.py                 # SQLite 事务、版本迁移
    workspace.py             # Git、快照、范围核对
    budget.py
    reuse.py
    verify.py
    review.py
    report.py                # 从结构化结果生成报告，不调用模型
    drivers/
      base.py
      fake.py
      selected.py            # M0 选中的唯一生产 Driver
  tests/
    unit/
    contract/
    integration/
    fixtures/
    live/                    # 默认不运行
  docs/
    architecture.md
    adr/0001-transport.md
    operations.md
  examples/
    project.json
    task.json
```

模块按真实职责拆分即可，文件数不是考核标准。先完成端到端纵切面，再根据耦合拆文件；不要先生成几十个空壳目录、插件接口和工厂。

### 5.3 三类数据严格分开

**项目契约**放目标仓库 `.hflow/project.json`，随项目版本管理，保存验证命令、禁止路径、默认风险策略，不保存凭据。

**本机绑定**放独立的 HFlow 用户配置目录，保存可执行文件位置、transport、Harness profile、模型逻辑别名和能力记录。它不属于 `~/.codex/`、`~/.claude/` 或 `~/.dsh/`，也不覆盖这些目录。

**运行数据**放控制器的本地数据目录，包含 SQLite、证据和受管工作区。它在业务工作区之外，但相同操作系统用户仍可能访问，所以“目录外置”不等于沙箱；第 14 节说明真实信任边界。

## 6. 项目接入与配置所有权

项目接入只生成必要的 `.hflow/project.json` 和最短入口说明；已有 `AGENTS.md` 采用可预览的受管块或用户手工引用，不覆盖全文。原文件冲突时报告，不擅自合并规则。

不得默认安装插件、修改全局登录态、迁移私有会话、扫描家目录找到“正确模型身份”、覆盖用户自定义命令，或者删除历史备份。

配置优先级为：**安全硬约束 > 项目已批准策略 > 本机能力约束 > 本次更严格的任务限制**。本次任务不能降低上层安全策略。放宽必须经过单独的明确授权，并绑定 plan/policy 指纹。

项目配置是声明式数据，不允许嵌入任意 Python 求值或从网络加载可执行规则。验证命令采用已经批准的命令 ID；TaskSpec 不能自己传入“验证成功”的 shell 命令。

`doctor` 默认只运行帮助、版本、依赖、权限配置和本地接口检查，不调用付费模型。未做 live 验收时显示 `NOT_LIVE_TESTED`，不能显示“模型与账号完全可用”。

每个会话不再遍历所有 Harness 的全局部署副本。只检查本次选中的运行组合；缓存静态探针，版本、二进制、profile、插件或执行环境变化时使相关探针失效。

## 7. DSH-first 适配：先复用、再认证，不盲目写桥

### 7.1 M0 首选：acpx 驱动官方 DSH ACP

先验证以下组合，而不是先实现自定义 DSH WebSocket、HTTP 网关、终端抓屏或日志解析桥：

```text
HFlow → acpx 自定义 Agent → 原生 DSH ACP profile → 原生 DSH Agent
```

DSH 文档中的源码仓启动形式是 `pnpm dsh --profile acp`。已安装 CLI 的具体启动形式应由本机 `--help` 和实际 profile 决定，不把源码仓命令直接假定为全局 CLI 命令。acpx 的自定义命令是其已有能力，不需要先把 DSH 加入它的内置 Agent 名单。[S3、S6]

M0 的检查包括：实际启动入口、stdout 协议纯净性、初始化和能力返回、新会话、一次任务、终止语义、模型配置、权限请求、中文/空格路径、Windows 下关闭后无遗留执行、错误输出与退出码一致性。

**首版使用一次性任务语义。** 每次任务/审查有独立 ID，不依赖 acpx 的透明重连续接。后续要启用会话复用，必须验证实际远端 session ID 未被替换，且重连失败不会自动重做已有变更。[S7]

### 7.2 不通过时的明确退路

如果 acpx 与本机 DSH 在必要行为上不兼容，M0 输出一个具体阻塞证据；不开始“修好整个 acpx/DSH 生态”的支线。

通过 ADR 将首版唯一生产 transport 改为 DSH 官方 headless。薄 Driver 只处理进程、输入、JSON 事件、结束状态和标准结果；不复写 DSH 工具系统。**没有静默运行时 fallback，也不同时维护两套生产实现。**

DSH headless 文档支持 stdin、JSON 事件与会话 ID，并明确说明 `final` 事件可能出现在失败的 turn 中。必须结合退出状态和错误信号判定结果，不能仅检查最后有没有 JSON。事件投影可能截断中间内容，不能拿它替代完整的验证证据。[S4]

### 7.3 兼容性记录粒度

记录 `os + arch + executable_version/hash + transport_version + profile_digest + relevant_plugin_versions + tested_capabilities`。不要要求每个业务项目随着 CLI 升级修改一份版本清单。

同一组合已验证的能力复用认证；发生相关变化时先跑无模型探针，再按受影响能力做小型 live 检查。版本变化不应触发所有测试、所有角色、所有模型的全矩阵重跑。

认证不保证某个模型的推理质量，也不保证订阅余量。ACP 的本地认证成功不代表上游模型账号有额度。DSH 的 context usage 也不能自动当成账单 Token。[S3]

### 7.4 后续 Codex 适配

Codex 可以通过原生非交互 CLI 接入；官方接口提供 `codex exec`、JSONL、结构化输出 schema 和会话续接。权限模式应显式设置，不沿用已经不合适的旧启动串。[S18]

核心只看到相同 Driver 契约。模型别名绑定在本机配置，不能要求 `CODEX_THREAD_ID` 才允许业务任务运行。DSH 默认 profile 中 Codex 预算为零；未来接入 Codex 需要显式更换 profile，而不是发生失败就自动升级到昂贵模型。

## 8. 工作流：两条风险路径，而不是所有任务走完整仪式

### 8.1 常规路径

```text
接收短 TaskSpec
  → 检查范围、验收、复用决策/豁免、预算
  → 创建独立工作区
  → 一个原生 Worker 完成修改
  → 冻结候选快照
  → 程序执行必要验证
  → 按风险进行一次独立审查
  → 接受候选并生成本地交付凭据
```

已有明确需求的小修改不额外做计划审。纯说明文案等低风险修改可以由范围检查和必要验证直接接受；涉及业务行为的修改默认需要独立审查。对“纯文档”的判断必须检查实际 diff，不能只相信任务标签。

### 8.2 严格路径

涉及认证授权、支付、个人数据、数据库迁移、删除、生产配置、依赖供应链、部署或扩大权限的任务，增加相应的设计检查和人工授权。

严格路径不是“固定十个专家同时审查”。按具体风险增加一个明确步骤，例如检查迁移回滚，或确认权限范围。额外步骤必须产生与原步骤不同的证据。

对外发送、发布、部署、删除及凭据操作由执行权限单独控制。代码本身通过审查，不等于已经被授权在真实系统中执行。

### 8.3 只保留四个语义角色

| 角色 | 是否常驻 | 职责 |
|---|---|---|
| Planner / Researcher | 否，按需 | 澄清实质缺口、寻找可复用实现、形成可执行 TaskSpec |
| Implementer | 每项开发任务一个 | 在分配范围内实现与说明变更 |
| Reviewer | 按风险 | 独立检查候选是否满足验收及关键风险 |
| Integrator | 仅实际集成冲突时 | 处理已接受结果之间的必要兼容修改 |

Verifier、Scheduler、Reporter、BudgetManager 都是程序模块，不是付费 Agent 角色。

领域专长通过简短角色补充和必要文件引用表达，不预建几十个职业身份和跨职业投票机制。

## 9. 状态、持久化、恢复与幂等

### 9.1 最小状态模型

任务状态：`DRAFT → READY → RUNNING → CHECKING → ACCEPTED`。

旁路状态：`BLOCKED`、`CANCELLED`。已知的可修复业务失败可以在预算内回到 `READY`，但必须创建新的 attempt。CHECKING 的当前阶段用 `verification / review / integration-check` 字段表示，不另造大量互相冲突的全局状态。

`ACCEPTED` 的意义是验收通过、候选交付物已冻结。是否已合入目标分支单独记录在 delivery 状态中：`LOCAL_CANDIDATE / INTEGRATED / PUBLISHED`。未发布的本地候选不能报告“已上线”。

每个 attempt 使用 `CREATED / ACTIVE / SUCCEEDED / FAILED / CANCELLED / OUTCOME_UNKNOWN`。用户取消或进程返回零，不直接改变任务验收状态。

### 9.2 唯一运行事实源

SQLite 是本机运行状态的唯一权威存储。建议表为 `runs`、`tasks`、`attempts`、`evidence`、`approvals`、`events`；早期可以更少，但不要为不同报告复制可修改状态。

同一事务中更新状态、预留预算、写事件。模型日志和大型测试输出放文件，数据库保存内容哈希与引用。JSON/Markdown 只是导出或任务输入，不同时成为运行时状态机。

一个项目同时只允许一个调度/集成控制器持有所有权。开始执行前事务性 claim；状态更新使用 revision 比较，不接受旧 attempt 的迟到结果覆盖新任务。

### 9.3 模型调用不是数据库事务

启动外部进程前，持久化 invocation ID、预算预留与 dispatch intent。启动后记录进程身份、启动时间、工作区、实际 session ID 和观测状态。

控制器若在“模型已执行，但结果尚未落库”时崩溃，不可能仅靠数据库重试保证恰好执行一次。恢复时标记 `OUTCOME_UNKNOWN`，检查已有进程、工作区 diff、持久结果和执行凭据；在确认原尝试停止且结果已处理前，不重新派发写入任务。

**租约过期不能单独证明 Worker 已停止。** PID 也必须结合启动时间/受管实例标识识别，不能杀掉 PID 重用后的无关进程。

### 9.4 恢复的顺序

先停止新调度，再核对运行中的受管进程，随后核对工作区和已产生证据。能够证明某步骤成功且输入未变化时复用结果；失败可确定时按错误分类处理；无法判断时停在 BLOCKED，给出最短恢复动作。

`resume` 的含义是继续任务状态机，不是无条件重放上一个 prompt。恢复不得自动产生第二份同样的补丁、第二次外部副作用或第二笔部署操作。

### 9.5 工作流自身不得热修复

每个 run 绑定控制器构建版本、schema 版本、policy 指纹、Driver 版本和任务规格版本。执行中的 Worker 不得修改控制器、认证记录、预算规则或已批准的验收命令。

工作流故障形成一个独立维护任务，由人决定是否值得做。修复后的版本用于新 run；当前业务 run 保留原语义、明确阻塞或结束。升级不能偷偷改写旧运行记录。

## 10. 成本预算：把止损写进执行器，而不只是提示词

### 10.1 默认预算建议

以下是初始策略参数，不是已经证明的最优值，也不是对你订阅额度的换算。

| 参数 | 常规任务默认值 | 说明 |
|---|---:|---|
| 同时运行的实现 Worker | 1 | 团队模式单独授权后才提高 |
| 原生子代理 | 0 | 先验证原生配额与取消传播 |
| 额外规划/研究 turn | 0 | 新组件/实质不明确任务可预批 1 |
| 实现 turn | 1 | 这是顶层任务 turn，不是底层 API 请求数 |
| 语义审查 turn | 业务变更 1；低风险文案 0 | 新会话，读取冻结候选 |
| 业务修复 cycle | 最多 1 | 修复及其必要复审一起预留预算 |
| 已证明未开始执行的传输重试 | 最多 1 | 结果不明的执行不适用 |
| 普通任务顶层 turn 总上限 | 4 | 首次实现+审查+修复+定向复审 |
| 预批研究任务总上限 | 5 | 在普通任务预算上增加一次研究 |
| 单次 Agent turn 截止时间 | 初始建议 15 分钟 | 可按任务调整；不是服务交付时间承诺 |
| 单 run 总时限 | 初始建议 45 分钟 | 包括已配置验证；超时不加预算自救 |
| 默认 Codex 调用 | 0 | DSH-only profile 的硬路由限制 |

大任务超出预算时先拆成独立可验收任务，不默认提高总上限。一个任务只有明确交付目标，才能获得单独预算。

### 10.2 必须区分三种计数

**顶层 turn/进程调用数**由控制器直接计数，可以硬限制。**Harness 内部模型请求、自动重试和原生子代理消耗**只有在相应能力可观察/可限制时才可精确约束。**服务商账单或订阅周额度**只有来源实际提供时才能记录。

不知道就写 `null/unknown`，不能写 0。估计 Token 与服务商实际计费 Token 分列；context-window usage 不能当费用。订阅百分比不通过“Token×价格”反推。

若原生 Harness 不能强制单 turn 的内部模型步数，界面必须标明成本上限为 best-effort，而不是承诺严格美元上限。时间限制及取消可以止损，但已发出的模型请求可能继续计费；记录取消后迟到的实际用量。

### 10.3 原子预算预留

每次派发前预留顶层 turn 和可用的用量额度。父任务和其所有子代理共享同一 run 预算，不为子代理重新开一个看似独立的免费池。

需要修复时，先确认“修复+必需验证+复审”整体仍有预算。没有就停止，不为了做最后一步而先无限追加前面的工作。

### 10.4 错误分类与动作

| 类别 | 例子 | 默认动作 |
|---|---|---|
| 传输未入场 | 可确认未提交任务的启动失败 | 一次有界重试；仍失败则阻塞 |
| 结果不明 | 连接断开，但进程或修改可能仍存在 | 先 reconcile，不重派 |
| 上游限流/额度不足 | 原生报限流、没有余额 | 停止或记录有界等待，不切到更贵模型 |
| 项目业务失败 | 测试暴露真实实现缺陷 | 同一任务内一次定向修复 |
| 环境失败 | 缺少工具、版本不兼容、服务不可用 | 阻塞并给明确动作，不让 Worker 自建整套环境 |
| 协议失败 | 缺关键结果、终止语义冲突 | 保留补丁和原文；不重做已经完成的编码 |
| 权限失败 | 越权写入、请求禁止操作 | 中止、隔离结果，需要授权才重新进入 |
| 工作流故障 | 控制器、适配器本身崩溃 | 结束业务尝试；另立维护任务 |

同样的输入指纹、失败签名和处理策略重复出现，必须触发 no-progress stop。Agent 改写一段总结或重新生成材料，不算真实进展。

## 11. Reuse-first：真正的准入门，也不能成为另一种材料税

### 11.1 何时需要研究

新增组件、引入依赖、设计通用框架、重写已有功能时，写代码前需要 ReuseDecision。已有架构内的小修复，只需确认仓内相关实现和已有复用决策；文案、格式等显然不涉及组件选择的任务允许明确豁免。

不要求每次修改都重新搜索 GitHub，不要求为了凑候选而列三家明显无关的项目，不强制付费搜索 Agent。

### 11.2 最短决策记录

记录放在 TaskSpec 的 `reuse` 段中即可，默认不新增报告文件：

```json
{
  "status": "decided",
  "need": "原生 DSH 的结构化自动化通信",
  "local_search": "记录实际检查过的仓内路径/已有依赖",
  "external_candidates": [
    {
      "repository": "openclaw/acpx",
      "inspected_ref": "50a47ad10a75431cbc276ec9b555d11fe1f69c84",
      "decision": "reuse_if_contract_passes",
      "required_fit_test": "DSH ACP 单任务、终止及权限语义互操作",
      "license_status": "MIT，采纳时核对所锁定版本"
    }
  ],
  "choice": "reuse",
  "reason": "已有标准客户端；只保留业务准入和预算语义",
  "revisit_on": ["接口契约变化", "必要安全能力失效"]
}
```

准入程序检查记录存在、引用有效、候选结论明确、必要测试是否完成或阻塞。它不能单凭字符串字段证明研究质量。重要取舍由一次语义审查或人工批准承担，而不是用无限材料替代判断。

### 11.3 必须先研究、再开放生产写入

需要新复用决策的任务，Researcher 使用只读/受限上下文，形成决策后才准入写入阶段。Worker 发现必须增加依赖或扩大范围时，返回变更请求，不直接安装新轮子或自己改任务规格。

仓库文档和下载的样例视为不可信输入，不让它们修改执行策略。禁止为了“验证一下”自动运行陌生仓库的安装脚本、CI、postinstall 或凭据相关命令。

### 11.4 对本项目的特别约束

每次新增功能必须先问：能否由 Git、SQLite、现有测试工具、原生 Harness 或已选客户端承担？不要复制 acpx 的通用会话管理，再把它称为薄适配；也不要为了彻底避免自研，整包引入会制造双重状态和隐性重试的大框架。

## 12. 验证证据：只运行必要检查，并明确什么时候不能复用

### 12.1 验证归属

Worker 可以为调试自行运行测试，但其文字“全部通过”不是正式验收证据。控制器在冻结候选上运行已经批准的检查，记录命令 ID、输入、工具版本、退出码、输出引用和结果。

首版不要为了消除一次必要的独立验证，先开发复杂的远程证明系统。最先删除的是同一个已冻结候选在多个阶段重复执行同一正式检查，而不是删掉独立验证本身。

后续可以允许 Worker 通过控制器的受控 verify 入口触发检查，从而把调试与正式证据合并；这一扩展必须保证 Worker 不能伪造 receipt 或修改命令目录。

### 12.2 证据 key

```text
evidence_key = H(
  完整候选输入快照,
  验证命令ID与argv,
  验证配置版本,
  依赖锁定与实际工具版本,
  影响结果的环境/服务/fixture/seed指纹,
  平台与适用的路径身份,
  检查选择及其理由
)
```

只保存 Git HEAD 不够，脏工作区和新文件也可能参与结果。候选必须由控制器冻结；验证前后核对输入未被并发改写。输出缓存目录和临时文件只有被明确声明为不影响输入时才排除。

不要记录原始秘密环境值；使用保密的本地比较机制或将相关检查设为不可跨运行复用。不要把低熵秘密的普通公开哈希当脱敏。

### 12.3 缓存默认范围

首版只做**同一 run、同一候选、同一命令、同一执行环境**的去重。跨运行和跨工作区缓存不是首版必需功能，待环境指纹和路径无关性经过验证后再开启。

跨分支集成、依赖变化、测试命令变化、工具版本变化、风险策略变化、外部服务状态变化，都会使相关证据失效。不能因为 changed files 列表看起来无关，就推定验证可安全跳过。

网络、时间、随机数、外部服务等非确定性检查默认不缓存，或使用明确的过期/快照策略。失败结果用于诊断，不作为“以后不用跑”的通过证据。

### 12.4 测试选择

优先使用目标项目现有的快速检查和针对性测试。只有项目有可靠的依赖影响分析时，才按影响范围缩小测试；否则走项目指定的必要集合。集成后的验证单独按最终树及环境判断，不直接引用分支 Worker 的旧结论。

Reviewer 默认读取已有通过/失败证据，不再命令式重跑整套测试。它可以请求一个**不同且必要**的检查，说明缺少了什么证据。

### 12.5 验证失败处理

环境问题不转交 Agent 无限修系统；真实代码问题允许一次针对性修复。修复改变了输入后失效重跑相关检查，这是必要验证，不算浪费。

已经存在的 flaky test 应记录原始失败和最多一次经过策略批准的重试；不允许一直重跑到绿，再把历史失败删除。

## 13. 审查：独立上下文、有限轮次、明确问题

业务变更的 Reviewer 使用独立原生会话，不继承 Author 的完整对话、推理和自我辩护。它读取 TaskSpec、必要项目约束、最终 diff、相关源文件和控制器证据。

“独立”指会话和证据路径独立，不保证相同模型没有相同盲区，也不要求必须购买第二家模型。

审查结果只需要：`accept / changes_requested / blocked`；每条阻塞发现提供具体位置、影响、理由或复现方式，以及必要修正。格式偏好、未纳入验收的扩展想法、主观完美主义不能阻塞交付。

常规路径最多一轮审查加一次定向复审。第二轮重点看原阻塞问题和新增 diff，不把所有历史材料再审一遍。新 diff 确实引入新风险时可以新增问题，但必须说明证据。

Reviewer 不写生产代码、不修改测试标准、不运行安装器、不调整预算。它声称 `writes_performed=false` 不是强只读的证明；实际权限等级必须来自 Driver 与运行环境，第 14 节详细规定。

禁止同一个 Agent 在同一会话改完代码、换一个身份提示词，就被标为“Fresh Reviewer”。

## 14. 安全与权限：承认边界，不用复杂文档冒充沙箱

### 14.1 三个最容易混淆的边界

Git worktree 是工作区隔离，不是安全沙箱。把状态库放到工作区外，是减少误写，不是同用户攻击隔离。ACP 权限回调或 cwd 参数，不能自动约束原生 Harness 内所有任意 shell 和文件系统操作。acpx 自身文档明确说明终端命令不是操作系统沙箱。[S6]

DSH ACP 不依赖客户端文件系统操作，所以 acpx 对客户端 `fs/*` 的限制不能直接当成 DSH 所有原生工具的写入限制。[S3、S6]

### 14.2 两种运行安全等级

**Trusted-local**：面向本人可信项目，使用独立工作区、最小原生工具集、后置范围检查和受控集成。这能减少意外损坏，但不能承诺抵御同一用户权限下的恶意命令。必须一次性清晰确认这一风险，不把它包装成强隔离。

**Isolated**：使用已经建立并验证的操作系统沙箱、独立低权限账号、容器/虚拟环境等边界，限制可写目录、敏感目录、网络与进程能力。具体机制按平台选择；本方案不要求所有人先新造一套沙箱。要求强只读或高风险任务时，环境不具备能力则拒绝自动执行。

首版可以先支持 Trusted-local 的安全子集，并让严格任务停在批准/环境检查处。不要为了宣称“全自动覆盖一切”，悄悄放开危险操作。

### 14.3 Reviewer 的可选等级

强审查模式必须通过真实只读权限/沙箱测试。缺少该能力时，可以在一次性候选副本里做可信本地语义检查，但结果必须标记为 `audit_only`，不能标记 `enforced_readonly`。

项目策略可以允许 audit-only 用于低风险可信代码；严格路径不允许自动降级。副本的存在不能证明原仓库和家目录不可达。

### 14.4 进程与命令

控制器以 argv 调用程序，避免把任务文本插进 shell。Windows 的 `.cmd`/启动器、引号、Unicode、路径大小写、符号链接/目录联接要单独验收。

取消必须覆盖被本次 run 拥有的进程及其受管后代，并确认其停止后才释放写入所有权。无法证明清理成功时保持阻塞。不要把 acpx 或系统的普通进程组行为说成所有逃逸守护进程都能被强制回收。[S8、S20]

### 14.5 凭据、外部副作用与供应链

不复制整个 Harness home，不把登录文件写进 Git，不把原始会话/推理日志默认塞入公开报告。子进程只获得必要环境；可信本地模式下仍要承认它可能具有读取同用户文件的权限。

安装依赖、网络发布、删除、数据库写入、生产部署必须有独立授权。项目测试也是可执行代码，对陌生仓库不能直接给予真实凭据和生产网络权限。维护者文档与 issue 只是输入材料，不能授予工具权限。

上游版本锁定到经过测试的发行版/commit；自动任务不使用 `@latest` 拉取新行为。检查 LICENSE、传递依赖、构建脚本与来源。采用代码时保留其许可证义务。

## 15. 工作区、交付与集成

每个写入 attempt 拥有一个受管工作区和明确 base。控制器在启动前检查目标仓库状态；不自动 stash 用户改动，不执行 `reset --hard`，不清理不属于本 run 的文件。

Worker 结束后，控制器验证文件范围、禁止路径和新文件，冻结候选。所需验收通过后，生成本地分支/补丁与机器可读 receipt。仅“模型说完成”或“进程退出零”不构成交付。

首版默认产出 **ACCEPTED 的本地候选**，不自动 push 或发布。项目可以预授权自动集成到指定分支，但这与模型是否有写入代码能力是不同权限。

集成由唯一 Integrator 执行：重新读取目标分支，比较预期 base，锁定候选，然后应用并验证最终树。目标已变化时停止或按已批准策略重做集成，不能沿用旧验收结论直接成功。实际 Git 冲突才触发有预算的集成修复 Agent；平时不用模型充当 merge 命令包装器。

冲突修复改动也必须验证，不能打着“只是胶水”的名义修改已批准接口、删掉有效测试或放宽验收。

删除 worktree、分支和运行数据是独立清理动作：先 dry-run，只清理已登记且无未交付改动的资源。失败和取消的工作区默认保留，方便人工取回有价值的补丁。

## 16. 最小契约、配置与命令设计

**本节所有 HFlow 字段、命令、接口都是待实现设计，不是现有 DSH/acpx 命令。** 上游具体参数由 M0 确认后在 Driver 内转换。

### 16.1 TaskSpec

一个任务只有一份当前批准的规格。用户修订目标时产生新 revision，不就地重写已开始 attempt 的输入。

```json
{
  "schema_version": 1,
  "task_id": "T-001",
  "revision": 1,
  "goal": "修复空输入导致的异常，保持已有正常输入行为",
  "acceptance": [
    {"id": "AC-1", "statement": "空输入返回约定的空结果", "check_ids": ["unit"]},
    {"id": "AC-2", "statement": "现有正常输入测试保持通过", "check_ids": ["unit"]}
  ],
  "scope": {
    "write_allow": ["src/parser.py", "tests/test_parser.py"],
    "write_deny": [".hflow/**", ".github/**"]
  },
  "risk": "standard",
  "dependencies": [],
  "reuse": {
    "status": "existing_decision",
    "reference": "project:parser-library-choice",
    "reason": "沿用现有解析组件，不新增依赖"
  },
  "review": {"required": true},
  "delivery": {"mode": "local_candidate"},
  "budget": {"max_agent_turns": 4, "max_repair_cycles": 1}
}
```

准入校验：非空目标；验收 ID 唯一；检查 ID 在可信项目目录存在；scope 不越过项目根或跟随联接逃逸；复用决策可解析且未失效；预算不高于预授权上限；风险不能比项目规则要求的等级低。dependencies 首版只支持已完成前置任务，后期才用于 DAG 并行。

### 16.2 本机 profile

```json
{
  "schema_version": 1,
  "profile_id": "dsh-local",
  "role_bindings": {
    "implementer": "dsh-default",
    "reviewer": "dsh-default",
    "planner": "dsh-default"
  },
  "agents": {
    "dsh-default": {
      "harness": "dsh",
      "driver": "selected-in-M0",
      "model_selection": "native_profile",
      "capability_record": "local-capability-record-id"
    }
  },
  "limits": {
    "max_parallel_workers": 1,
    "max_native_children": 0,
    "codex_agent_turns": 0
  },
  "security_mode": "trusted_local"
}
```

`selected-in-M0` 是设计占位符；实际配置必须是已经安装并认证的 Driver ID，否则拒绝运行。逻辑 agent 名称可以稳定，实际 provider/model/effort 在本次 run 中解析并记录；不把模型永久锁在角色定义里。

### 16.3 核心 Driver 契约

用 Python Protocol/抽象类定义以下方法即可，不开发插件市场或动态代码下载器：

```python
class HarnessDriver(Protocol):
    def probe(self, binding: Binding) -> CapabilityReport: ...
    def start(self, request: InvocationRequest) -> InvocationHandle: ...
    def observe(self, handle: InvocationHandle) -> Iterator[NormalizedEvent]: ...
    def cancel(self, handle: InvocationHandle) -> CancellationReceipt: ...
    def reconcile(self, handle: InvocationHandle) -> ReconcileResult: ...
```

`probe` 默认不调用模型。`start` 必须拿到已经授权的 role、cwd、输入包、截止时间、能力要求和 invocation ID；不能自行增大权限或切换模型。

`NormalizedEvent` 只表达 `started / progress / usage / permission_requested / completed / failed` 等必要语义，允许保留受控的原始事件引用。不要强行把不同 Harness 的内部 thinking、tool call 和压缩事件改造成一份假装完全等价的历史。

`cancel` 返回 `confirmed_stopped / still_running / unknown`，不是固定 true。`reconcile` 不得自己发起新的模型工作。

### 16.4 控制器生成的 ResultReceipt

Agent 只提交候选变更与简短说明。核心结果由控制器生成，不要求 Worker 写一份大型 JSON 才能承认它已经改好了代码。

```json
{
  "schema_version": 1,
  "run_id": "R-example",
  "task_id": "T-001",
  "attempt_id": "A-001",
  "task_revision": 1,
  "runtime_build": "resolved-build-id",
  "plan_digest": "computed-digest",
  "harness_outcome": "completed",
  "candidate": {"base_commit": "resolved-base", "tree_hash": "computed-tree"},
  "verification": {"status": "passed", "evidence_ids": ["E-001"]},
  "review": {"status": "accepted", "isolation": "audit_only"},
  "task_state": "ACCEPTED",
  "delivery_state": "LOCAL_CANDIDATE",
  "usage": {
    "agent_turns_observed": 2,
    "provider_billed_tokens": null,
    "provider_cost": null,
    "subscription_quota_remaining": null
  },
  "limitations": ["示例；实际隔离等级与计费来源由运行证据决定"]
}
```

样例值不代表实际运行数据。真实 receipt 中的版本、摘要和证据必须由程序计算，模型提供的同名字段不能覆盖。

### 16.5 Reviewer 最短输出

```json
{
  "verdict": "changes_requested",
  "findings": [
    {
      "id": "F-1",
      "location": "src/parser.py:42",
      "impact": "空输入仍走到非法索引",
      "evidence": "对照 AC-1 与该分支可复现",
      "required_fix": "提前返回约定的空结果"
    }
  ]
}
```

优先使用 Harness 原生结构化输出；不支持时只请求一个最短对象，并进行确定性解析。遇到格式错误，保留代码、原始意见与已完成证据；不能重跑完整实现只为补 JSON。不得靠无限“请严格遵循格式”回合修复工作流。

### 16.6 便携 Handoff

换 Harness 时传递 TaskSpec、批准的设计/复用决策、base 和候选树、已完成证据、未解决 finding、剩余预算及必要源文件引用。不要传递厂商私有 session 文件，或把所有原始对话当必须恢复的数据。

Handoff 不保证无损移植某个 Harness 的内部上下文；它保证项目目标、事实和已验证结果可独立重建。目标 Harness 重新做能力准入，不能继承来源 Harness 的权限认证。

### 16.7 命令面

首版实现 `doctor`、`run`、`status`、`cancel`、`resume`、`report`。项目接入与本地交付可先是明确文档/薄命令，确认重复需要后再增加 `init`、`integrate`、`clean`。

示意：

```text
hflow doctor --profile dsh-local
hflow run --task task.json --profile dsh-local
hflow status R-example
hflow cancel R-example
hflow resume R-example
hflow report R-example
```

`status/report/doctor` 默认零额外模型调用。`run/resume` 的进度由程序事件显示，不付费生成持续状态解说。进度终端至少展示当前步骤、已消耗 turn、剩余预算、候选状态和阻塞原因。

## 17. 最终的 Agent Team + 原生 Subagent 混合架构

### 17.1 什么时候打开并行

先证明顺序闭环有净收益。并行只对依赖关系明确、可独立验收、写入范围不冲突、集成成本可控的任务开启。默认最多两个写入 Worker；数量根据真实资源、调用预算和合并成本调整，不以 CPU 核心数决定 Agent 数量。

不因一个任务涉及前后端，就自动创建架构师、产品经理、前端、后端、测试、安全、文档和总结八个 Agent。

### 17.2 唯一调度所有权

外层控制器拥有 Task DAG、ready/claim、工作区、预算和集成。Planner 可以提议任务图，程序验证无环、依赖存在、范围合法、预算可覆盖后才执行。

每个 Worker 必须明确完成条件、输入依赖、输出接口和唯一写入范围。共享 lockfile、迁移序列、公共接口和配置等冲突热点，按资源锁串行处理；不能仅靠目录不同判断独立。

不得同时让外层控制器和 `dsh-agent-teams` 自己的调度器接管同一个 Task DAG。后者如果被采用，要么完整作为某个封装任务的内层实现，要么被单独验证为委派后端；都不能再当第二个外层事实源。[S16]

### 17.3 原生子代理不是外层团队的替代品

```text
控制器
 ├─ Worker A：原生 DSH
 │    └─ 可选原生 DSH 子代理：只读调查一个局部问题
 └─ Worker B：另一原生 Harness
      └─ 使用该 Harness 已验证的原生子代理能力
```

原生子代理由其父 Harness 创建，不让另一家的聊天 API 假扮。首个可开放场景建议是只读代码检索或独立问题分析，而不是让子代理和父代理同时改同一目录。

### 17.4 子代理准入

必须可确认：深度限制、数量限制、父预算传递、取消传播、工作区权限、结果归属、用量可见性。默认嵌套深度最多 1，每个父 Worker 至多 1 个子代理；全局模型活动槽位初始最多 2，父 Agent 与子代理同时产生请求时都计数。

原生实现无法暴露或强制其中某个必要限制时，该模式标记不支持，不用提示词“最多两个”冒充强配额。可以保留同 Harness 无子代理模式继续工作。

### 17.5 角色动态化的范围

可以按任务传入领域专长和输入/输出约束，但角色不能动态发明新的权限等级、批准自己的范围扩张或给子代理另开无限预算。技术负责人也只是一个角色，不是永远必须使用某个高价模型的系统身份。

## 18. 实施顺序与每阶段交付

**按验收结果推进，不按日历自动进入下一阶段。** 以下是完整路线，不意味着第一轮让 DSH 一次性实现全部功能。

### M0：可运行前的最短决策与兼容性试验

交付：新仓库骨架、短架构说明、选型 ADR、真实本机能力记录、Fake Driver 的基础契约。

先检查本机 Python/Git/DSH/acpx 与相关 profile；不自动升级、不复制家目录、不额外启动 Codex。先用 mock ACP 服务测试客户端调用与异常处理，再在明确批准的试验中验证一次 DSH 任务和一次独立会话。该小型 live 试验建议最多 2 个额外 Agent turn，更多测试尽量用 fake 服务完成。

退出条件：确定唯一生产 Driver，列清支持和不支持的能力。acpx 不满足必要契约时，按第 7 节切换到 headless 路线，**不是同时开发两套**。两条都无法满足最低运行条件时，停在明确缺口，不追加第三个通用框架。

### M1：离线控制器纵切面

交付：TaskSpec 校验、状态机、SQLite、预算计数、Fake Driver、一次成功与一次失败的完整 receipt。

此阶段不连接真实模型。测试已经完成、预算耗尽、进程失败、重复提交、迟到结果、控制器中途崩溃、恢复后不重复派发等情况。优先将关键故障变成可重复测试，不先建设漂亮 UI。

退出条件：相同测试反复运行不产生重复 accepted 结果；状态/预算/事件事务一致；未知结果不会自动重跑。

### M2：DSH 单 Worker 真正交付一个小变更

交付：选定 Driver、独立工作区、冻结候选、必要验证、状态显示和本地候选交付。

选一个可独立验收的小型真实任务，例如增加输入边界处理和回归测试。不要用“重写工作流自身的全部功能”作为首次验证对象。

退出条件：DSH 实际产生可用变更；控制器完成验证并给出证据；无 Codex 调用；不修改 Harness 全局配置；出现失败能保留补丁且停止。

### M3：可日常使用的 v0.1

交付：复用准入、按风险审查、一次修复 cycle、同 run 验证去重、崩溃 reconcile、能力失效检查、自动报告与受控清理。

至少覆盖一项普通修复、一项需要复用决策的新功能、一项有环境失败的任务、一项主动取消任务、一项包含业务失败后定向修复的任务。

退出条件：下节关键验收全部通过，且对比直接 DSH 的代表性任务，没有出现明显“工作流维护替代项目推进”的退化。没有通过前，不开启 Team 与子代理。

### M4：证明真正的 Harness 可替换

交付：第二个真实 Harness Driver、同一任务包与验收在两端的契约测试、可解释的 Handoff。

第二个 Harness 可以是之后重新启用的 Codex，也可以是其他具备所需原生能力的工具。只使用事先限定的试验预算，不要求恢复当前大量 Codex 消耗。

退出条件：换 Harness 不修改 controller/contracts/项目验收，只调整 Driver 与本机绑定；同一业务验收能够成立；恢复/取消/权限不足不产生静默降级。

Fake Driver 是开发证明，不是第二个真实 Harness；仅通过 fake 不能宣布完成通用性认证。

### M5：有证据才增加团队与原生子代理

交付：简单依赖任务图、两个外层 Worker、资源锁、顺序集成、父子预算/取消传播以及一个受限原生子代理场景。

退出条件：至少一个适合并行的任务组在同质量标准下缩短总耗时，且协调/集成/额外 Token 没有吃掉收益。不适合并行的任务仍默认单 Worker。

## 20. 如何判断新系统真的省，而不是“看起来更专业”

### 20.1 先设直接 DSH 基线

比较对象首先是**相同验收标准下的直接 DSH 单 Agent 工作**，不是一定要再次运行已经很贵的旧工作流。旧日志可用时才作为补充基线，不为了证明新方案而再次烧大量 Codex 配额。

选择覆盖小修复、新功能、测试改进、研究取舍和环境失败的代表任务。记录难度、输入信息、允许工具与验收一致性；避免把已经被前一轮解决的答案偷偷提供给后一轮。

小样本只支持方向性判断，不声称统计显著节省。先匹配任务难度并轮换执行顺序，再决定是否扩大评测。

### 20.2 建议最少记录的指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 已验收任务数 | 满足预先批准验收条件的任务 | 核心产出 |
| 每任务顶层 turn | 控制器实际提交的 Agent turn | 识别流程膨胀 |
| 原生模型请求/Token/费用 | 只有真实来源可用时记录 | 解释内部成本 |
| 人工介入次数与原因 | 语义授权、环境修复、工作流故障分别记 | 区分必要和不必要摩擦 |
| 工作流维护开销 | 运行器修复、无进展重试、重复材料活动 | 直接对应旧痛点 |
| 无必要重复验证数 | 完全相同有效输入/环境的正式检查重复执行 | 检查去重是否生效 |
| 总耗时与等待耗时 | 从准入到交付，区分模型/验证/等待 | 判断并行是否有净收益 |
| 缺陷与验收回退 | 交付后发现的违反验收问题 | 防止省钱靠降质量 |

### 20.3 初始退出/发布目标

硬约束：默认 Codex 0 调用；状态查询 0 额外模型调用；当前业务 run 的工作流自我修复 0 次；无上限重试 0 次；未授权全局配置修改 0 次；同输入同环境的无必要正式验证重复 0 次。

软目标：经观察后，额外控制/协调开销尽量低于总任务资源的约 15%。这个百分比是试运行目标，不是本次测得的节省率；用量不完整时不能算一个假精确百分比，应改看可直接观测的 turn、时间和人工介入。

若 v0.1 在代表性任务上持续比直接 DSH 更贵、没有提高质量或降低风险，就暂停功能扩展，删除没有净收益的流程。先修产品方向，不继续添加“防止失败的新规则”。

## 21. 旧系统如何退役，而不是给新系统继续制造负担

先把旧仓库保持在可追溯状态。本方案不会代你归档、删除或修改仓库。

在你实际迁移时，保存旧仓库 commit、仍然有效的用户约束和少量典型故障案例。无需把每次历史重试、每份阶段报告和全部认证记录转换到新系统。

新系统先在全新测试项目或独立 clone 中运行，不触碰旧业务工作区。两套控制器不得同时持有同一个项目的写入权。项目切换时先停旧运行器，确认无活动 Worker，再接入新配置。

默认停止旧系统的全局自动检查/自动部署入口，应通过明确、可预览的本机操作完成，不由新安装器递归清理 `~/.codex/`、`~/.dsh/` 或 `~/.claude/`。

即使有些旧脚本可以复用，也先把它们当外部候选：单独判断职责、依赖、故障和测试。只有一个干净的小函数比现成库更合适时才按许可证采纳；不整包导入旧 Team runtime。

## 22. 日常使用应该是什么体验

一次正常业务任务，你看到的应该是：目标与验收、当前实际阶段、预算、最后变更与验证结论。不是几十份计划/交接/复审材料。

例：

```text
任务：修复空输入错误
运行：R-...
阶段：审查
预算：已用 2/4 个顶层 turn；原生计费用量暂不可用
候选：2 个文件变更，已冻结
验证：unit PASS，未重复执行
审查：独立会话，可信本地审查（非强沙箱）
交付：完成后输出已验收本地分支，不自动发布
```

失败时，输出“哪里失败、是否有可保留补丁、为什么没有重试、下一步是什么”。正常阶段自动推进；只有确实需要扩大权限、调整验收、解决模糊结果或追加预算时才请人决策。

最终报告由 receipt 和证据自动生成。不得额外调用一个高级模型，把同样的信息重写成第五份总结。

## 23. 开发红线：避免重演这次重写的起因

1. 不从旧运行器继续改，不把新仓库当旧系统的新分支。
2. 不把模型、Harness、角色、transport 写成同一个身份。
3. 不把 Codex 变成默认运行前置，不自动切到高价模型。
4. 不用 LLM 轮询状态、计数、重复组织已经结构化的材料。
5. 不把先找轮子变成所有任务都必须撰写长研究报告。
6. 不让两个调度器和两份状态数据库同时拥有同一任务。
7. 不把 final/exit 0/自报通过等同于验收通过。
8. 不把 worktree、cwd、提示词只读等同于操作系统沙箱。
9. 不在结果未知时自动重新派发写入，不承诺无法保证的 exactly-once。
10. 不为第一版预建多 Agent 平台、可视化 IDE、通用 DSL 或插件市场。
11. 不让业务 Worker 自动修工作流、安装全局插件或放宽自己的验收。
12. 不以“功能已经做出来很多”替代真实任务的净收益验证。

**最终应该得到的是一个可以随时换执行工具、知道何时停手、把结果交付出来的轻量开发控制器。不是一个需要持续消耗模型额度才能维持运转的 Agent 平台。**
