## 3. Store 修复：验证事务边界，不只是关闭线程检查

`check_same_thread=False` 允许跨线程访问；它本身不建立 HFlow 的业务原子性。单共享连接加 RLock 可以是当前小型实现的合理修复，不因此改成 ORM、连接池、异步数据库或后台数据库服务。

检查下面的边界；已经满足则保留，不重构：

- 同一连接上的执行、读取结果、commit/rollback/close 都有一致保护。需要返回多行时，在锁内物化为普通数据，避免把仍使用该连接的游标/懒迭代器带出锁外。
- 预算预留与 attempt、cancel_intent、验收 CAS 等复合操作，锁覆盖完整事务，不是在每个 SQL execute 外分别加锁。
- 锁和数据库事务不跨越等待 Agent、observe/collect、进程 wait/join 或外部工具执行；后台任务等输出时，取消线程必须仍能落库。
- 保留已有 SQLite 事务/约束/CAS。进程内 RLock 不替代跨进程数据库并发控制。

复用现有取消竞态测试，使用 Event/Barrier 等确定性同步，覆盖两个顺序：取消意图先提交则迟到成功不得 ACCEPTED；验收先提交则后到取消不得改写历史。再确认后台执行等待时主线程能够取消，异常路径释放锁并回滚必要写入。

不要用长 sleep 或反复执行一百次赌竞态。测试同步点不能制造“线程 A 持锁等待线程 B 获同一锁”的人为死锁。新增线程回归必须使用与报告场景一致的真实 Store 和真实线程，而不只 mock Store 方法。
